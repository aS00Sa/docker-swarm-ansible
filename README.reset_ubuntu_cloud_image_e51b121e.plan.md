# Сброс системы до состояния свежего Ubuntu Noble cloud image

## Что значит «как образ»

Файл [noble-server-cloudimg-amd64.img](https://cloud-images.ubuntu.com/noble/current/noble-server-cloudimg-amd64.img) — это **шаблон диска**: после первой загрузки меняются machine-id, журналы, кэши, установленные пакеты, данные в `/home`, сетевые/SSH ключи, состояние **cloud-init** и т.д. Полностью вручную «вычистить до байта» как оригинал почти нереалистично и не нужно.

Практическая цель обычно одна из двух:

- **A. Как после первой установки с cloud-init** (новый инстанс с тем же user-data).
- **B. Полностью пустой диск, как в .img до первой загрузки** (редко нужно; чаще — пересоздать ВМ/том).

## Варианты по среде

### 1. Облако (AWS, Azure, GCP, Hetzner, …)

Надёжный путь: **удалить инстанс и создать новый** из того же family образа (Ubuntu 24.04 Noble) с тем же cloud-init / Terraform / Ansible. Снимки диска «до порчи» можно откатить, если делали snapshot — но это уже не «как скачанный .img», а «как в момент снимка».

### 2. Своя виртуализация (KVM/QEMU, Proxmox, libvirt)

- Сохранить **оригинальную копию** `.img` (или использовать `backing_file` + отдельный overlay qcow2).
- **Сброс:** удалить ВМ/диск с изменениями и **создать новую ВМ с чистой копией** образа (или новый overlay поверх неизменённого base).
- Если нужно **повторить первую загрузку cloud-init на том же диске** (golden image, тесты): после подготовки иногда делают `cloud-init clean` (см. ниже), затем выключение и клонирование — но это не откатывает все пакеты и файлы, только часть «идемпотентности» первого бутa.

### 3. Контейнеры на хосте (LXD/Incus, systemd-nspawn)

Проще всего: **удалить инстанс и поднять заново** из образа `ubuntu:24.04` / cloud variant — это ближе всего к «как из коробки».

### 4. Физический сервер или один системный диск

Эквивалент «как .img» — **переустановка**: загрузка с установщика/живого образа и **полная перезапись** разделов или `dd`/restore образа на диск (с потерей всех данных). Точечная «уборка» не гарантирует идентичность шаблону.

## cloud-init: когда имеет смысл

На уже установленной системе команды вроде `sudo cloud-init clean --logs` (и при необходимости сброс machine-id по документации дистрибутива) помогают **снова выполнить cloud-init при следующей загрузке**. Это **не** удаляет пакеты, пользовательские данные и произвольные изменения в ОС — только очищает/сбрасывает часть артефактов cloud-init для повторного первого прогона (сценарий кастомных образов и лабораторий).

Официальная логика и флаги — в документации Ubuntu/cloud-init для вашей версии.

## Подход «список пакетов образа → удалить всё остальное»

Идея: взять **канонический список пакетов** с того же cloud image, что вы считаете эталоном, и на целевой машине удалить пакеты, которых **нет** в этом списке (или не сводить к точному совпадению версий — только к множеству имён).

### Откуда взять эталонный список

Рядом с образом на [cloud-images.ubuntu.com/noble/current/](https://cloud-images.ubuntu.com/noble/current/) лежит файл **`noble-server-cloudimg-amd64.manifest`**: по одной строке на пакет, формат `имя версия` (иногда имя с архитектурой, например `bind9-libs:amd64`).

Важно: каталог **`current/` меняется ежедневно**. Для честного сравнения нужен manifest **той же сборки**, что и ваш `.img` (или сохранённая копия manifest вместе с образом в артефактах). Иначе diff будет шуметь из‑за обновлений безопасности в образе vs на диске.

### Практический алгоритм (концептуально)

1. Сохранить эталон: из manifest получить отсортированный список **имён** пакетов (первое поле строки; при необходимости нормализовать `:amd64` для сопоставления с `dpkg-query`).
2. На целевой системе: `dpkg-query -W -f='${binary:Package}\n'` (или эквивалент), отсортировать, сравнить с эталоном (`comm`, скрипт, Ansible).
3. Множество «лишних» = установлено на хосте, но **нет** в эталонном списке. Для каждого кандидата — сначала **`apt-get -s remove`** / симуляция, затем осторожное `apt purge` пакетами с проверкой зависимостей.
4. После чистки: **`apt autoremove --purge`**, при необходимости **`apt --fix-broken install`**.

Пакеты из эталона, которых **нет** на хосте (пропали при ручных удалениях), обычно добирают **`apt install`** по списку — иначе система может остаться в «дырявом» состоянии.

### Ограничения (этим методом **не** получить полный «как .img»)

- **Не трогает состояние вне dpkg**: конфиги в `/etc`, данные в `/var`, пользователи, ключи SSH, **snap**/flatpak, контейнеры, бинарники в `/opt`, артефакты в `/usr/local`, **machine-id**, журналы.
- **Риск поломать загрузку/сеть/SSH**: метапакеты ядра, прошивки, облачные агенты провайдера могут не совпадать с generic manifest; провайдерские образы часто **не идентичны** `noble-server-cloudimg-amd64.manifest` с сайта Ubuntu.
- **Удаление «не из списка»** может снести зависимости, которые всё ещё нужны пакетам из списка, если эталон и фактическая система уже разошлись (частичное обновление, held packages).
- Версии в manifest — **эталон версий в образе**; гнаться за полным совпадением версий через purge/install обычно дороже и хрупче, чем сравнение по **именам** пакетов.

Итог: подход с manifest — разумная **аппроксимация «минимальный набор как у server cloud image»** при жёстком контроле baseline и тесте после перезагрузки; для строгого «как свежий диск» по-прежнему надёжнее пересоздание тома/ВМ из оригинального `.img`.

## Рекомендация

- Если нужна **чистая Noble как с маркета**: пересоздать машину/диск из **неизменённой копии** cloud image + ваши user-data/secrets.
- Если цель — **почти тот же набор deb-пакетов, что в образе**: эталонный **`noble-server-cloudimg-amd64.manifest` той же сборки** + diff имён + осторожный `apt purge` / добор недостающих + `autoremove`, с пониманием ограничений выше.
- Если нужно **только переинициализировать cloud-init**: `cloud-init clean` + понимание ограничений выше.
- Если среда не ясна (облако vs KVM vs железо) — выберите один сценарий из разделов 1–4; от этого зависит единственный «правильный» способ без потери данных вне системного диска.

## Связь с этим репозиторием

В этом репозитории (docker-swarm-ansible) упоминаний cloud-init/noble не найдено; автоматизация сброса образа, если понадобится, была бы **вне** этого репо (IaC провайдера, скрипты гипервизора или runbook).
